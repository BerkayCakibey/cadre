# Cadre — how to use it (quick reference)

This reference describes the commands of the repository code; the runtime copy is not assumed to be the same version. A definite permission is bound to the action, command, target, product, policy and plan version. After the first approval the full command is shown; commit/push/merge does not start before the required second, separate answer. An earlier approval or the CADRE_ONAY environment does not permit a new action.

Command names, CLI flags, JSON field names and reason codes are Turkish identifiers; the glossary is in [docs/ARCHITECTURE.md](../docs/ARCHITECTURE.md#glossary).

- `cadre` opens the full-screen panel in the terminal; without Textual or with `CADRE_ESKI_MENU=1`, the old menu. Without a TTY the menu does not open; use `cadre gorev "text"` or stdin.
- Full-screen interface: `cadre` with real data, `cadre tasarim` with sample data (a live copy of an expected run). Keys: ← → section, ↑ ↓ select, → or Enter open, ← or `q` back, `o` read the file, Shift+↑ ↓ scroll the detail, `n` new task, `Esc` quit. The language (Turkish, English) and the colour palette (Gruvbox, Everforest, Rosé Pine, Tokyo Night, Dracula, Catppuccin Mocha) change from Settings with Enter; `CADRE_DIL=en` starts the panel in English. Old menu: `CADRE_ESKI_MENU=1 cadre`. (The Textual environment is `~/.local/share/cadre-ui-venv`, path `CADRE_UI_PYTHON`.)
- New project: `cadre init [--olustur] [--tur python] [folder]` is the local project registration path; in an empty folder the first commit is made with two-step definite permission (CR-46 closed), `--olustur` creates the folder. `--tur python` (CR-33) puts a deterministic skeleton into the same permitted first commit (the file list is shown in the approval text); after registration `make install` (local `.venv`, no download) / `make test` / `make run` are written in a single record to `projects/<name>/iskelet.json`, and the QA command becomes `make test`; the only supported type is `python`. The panel's typed new-target input creates no folder or Git; once the plan is accepted the task waits with `new-project-init-permission-required`, `cadre init --olustur <folder>` takes the first commit permission, and when the task is restarted the same record registers the project under the name in the request, pins the source and continues (15.10).
- Task: in a registered repo `cadre` → `n` opens the three-step typed form; submitting creates a record at the plan gate. The old `cadre gorev` and, in the line menu, "Yeni görev ver" → paste → Enter twice on an empty line or `go` alone are the execution path. This old path runs unattended in an isolated `cadre/*` worktree, from the active branch
  (uncommitted changes included); if it fails it continues with `-c`; when it ends the run ledger is written.
- Live stream: thinking, tool calls (input/output), sub-agents, guard decisions, counters on the bottom line.
  Keys: `q` quit (the job continues) · `x` cancel · `t` show thoughts in full · `p` pause.
- `opencode` = the real opencode (interactive). For unattended mode always use `cadre`.
- Ledger: `cadre defter` → transcript.md / meta.json / motor.log / izleyiciler/ / degisiklik.patch / config-snapshot/.
- Development verification runs with `bash engine/tests/regression.sh` at the source repository root. The installed runtime is not assumed to contain the repository's `docs/` and Git context; the development gate uses the source checkout. Numbers are not written by hand: the script's last line is authoritative. The local gate is archived by default to the repository's `.tmp/test-arsivi/regresyon.jsonl` record (changeable with `CADRE_TEST_ARSIVI`);
  only the permitted live scenarios (`tests/canli_senaryo.py C01..C07`) write to `reports/test-arsivi/<C-id>-<stamp>/ozet.json`. The small acceptance package R01–R07 runs with `tests/kabul_paketi.py R0x --fixture-dir <fixtures> --yol sahte|go|or`: `--yol sahte` is a dry run (`kabul_sahte.py`, not a live acceptance), the live paths are subject to the same definite permission rules; the summary is `<output>/ozet.json` and `kabul-paketi.jsonl`. Product acceptance commands run in the engine's evidence sandbox; `--paket-tavan` protects the shared cap of the whole package with the `<output>/../kabul-paketi-pay.json` ledger (an N+1 allocation is denied); `--yalniz-oneri` takes the engine's permission proposal without approval/call; `CADRE_ZINCIR_<ROL>` is carried to the subprocess, a chain outside the allowed provider is denied. Before a sandboxed acceptance command the writable areas go through the FIX-25 hardlink preflight; the shared share ledger is re-read under a file lock.

On a target the user chooses a ready backlog, a goal to plan or a plan only; the plan is verified against the real repo/source and reviewed in a separate clean read-only session. With plan-only no implementation is opened. The result is compared with the original request; code acceptance and review/report/research acceptance are separate. Explicit difficulty–preference–role rules, a review in a separate session with the same strong model and flexible internal budget shares within a fixed total are the goals of the current contract. Fast spending alone is not a stop. These are not new CLI options or finished features; CR-18/30/32/35 are open (CR-39/42 closed). The permanent product essence is at the top of the contract in the source repository.

Current plan view and change goal: every job starts with a measured recorded plan; the plan can be read before implementation and during the job. Normal implementation runs after the system review. A user change request is handled with a safe stop and a new plan version/review; only the next implementation of a plan output requires current source/permission/budget verification. This paragraph announces no new CLI flag/command; the existing save-plan and automatic replan are not the whole of this protocol (CR-32/36/42).

## Plan and operation record

Normal and project OpenCode calls bound to a Cadre record handle files with the protected `bash` tool. The macOS sandbox limits reads to the selected source, the working tree, the temporary area and the required tool roots; plan/review cannot write the source, a typed implementation can write only the recorded task files. The network, Git metadata writes, control records and known secret paths are closed. If the sandbox cannot be set up the executor does not start. Direct QA, the start check and formatting commands bound to the run record use the same macOS sandbox; QA gets only the allowed tool/discovery environment. If the control profile cannot be published or the sandbox cannot be set up the test process does not start. When QA/baseline/format and observed OpenCode processes end, their own temporary area is cleaned with an identity check; evidence files are kept. Since a Claude tool sandbox is not supported yet, a normal/project Claude call waits for the environment before starting; the presence of the existing selection/session code is not execution support. OpenCode starts with a config and home root that are attempt-specific and not writable; only the Cadre plugin loads, an extra plugin/MCP waits for the environment before starting. Global/working-tree config plugins and the Node/Bun preload environment are not inherited. The installed 1.18.31 was verified without installing the SDK; the catalogue is not downloaded automatically. Another CLI version or a real model acceptance cannot be inferred from this local debug evidence. The owned temporary area of a stop observed in recorded worker and QA/baseline/format processes is cleaned up; evidence is kept. With the native sandbox permission signature and the protected process/owner/inode receipts, a grandchild that closes its descriptor and opens a separate session after the observer dies is also cleaned up as owned. An unobserved death of the OpenCode main process requires the armed receipt of the combined hook; a live/foreign/old/broken scope is not deleted and waits for automatic revival; a definite session hand-off is kept separately. Existing Node/Python dependencies can be read/run; tool and QA processes cannot change dependency stores and cannot read/run known installers or secret paths. Source/plan/product identity checks protected names and hardlinks before content. An approved inner-prefix npm diagnosis allowed an install before the final protection; in the final code a separately permitted real npm attempt was denied with EPERM while creating node_modules, and no package was installed. The CR-34 isolation acceptance of the supported environment is closed; the general action approval record and the final evidence of the delivery lifecycle are kept separately in the state. Other platforms are not considered supported; this profile does not replace all definite permission rules.

In the panel, task → Decision and operation shows the recorded wait/retry/remaining scope, the fixed total and the stage cap, and the last routing candidate/rejection reasons. The CLI `cadre devam` and the panel Start/continue use the `kosu.py start` entry; repeating it does not start the same live job again. `harcama-onay` does not change the cap, the provider quota or the `retry_after` value. New typed requests do not run without two task-specific call approvals.

The internal commands below use the `python3 engine/lib/kosu.py` prefix. The existence of a command is not permission for a paid call or a definite external action.

| Command / stdin | Behaviour |
| --- | --- |
| `plan-show RUN_ID` | Immutable revisions, the current review/changes and execution plan parity; read-only |
| `plan-backlog RUN_ID BACKLOG_PATH` | Binds an immutable snapshot of an explicitly chosen in-repo backlog to an old, untyped run; calls no model, gives no budget/permission. The source of a typed input cannot be changed |
| `plan-answer RUN_ID REVISION DECISION_ID` / answer text | Records the operator's version/source-bound answer to a critical question; gives no budget/permission and calls no model |
| `plan-change RUN_ID CHANGE_ID REVISION` / change text | A request to stop new steps, with version and single-request checks; no claim of a real stop |
| `plan-stop RUN_ID CHANGE_ID` | Stop confirmation with a product/cost snapshot once the main/child ownership and attempt locks are free |
| `plan-withdraw RUN_ID CHANGE_ID` | Withdrawal after a stop; an explicit continue decision is expected |
| `save-plan RUN_ID MODEL [CURRENT_REVISION]` / plan JSON | Adds the first plan or a revision after a confirmed stop to the journal; an old version is rejected |
| `plan-review RUN_ID REVISION OPENCODE_EXECUTABLE` | A separate clean read-only review with the real transport; may call a model/provider, needs definite permission and a cap beforehand |
| `plan-resume RUN_ID CHANGE_ID REVISION` | Records the continue decision with the current PASS/source/cap; starts no process |
| `request-proposal RUN_ID` | A concrete permission proposal for the source/request/model routes/time/fixed total; starts no call |
| `request-approve RUN_ID [CONFIRMATION]` / proposal JSON | The first approval returns a nonce; a separate second approval authorizes the same proposal, starts no call |
| `request-plan RUN_ID` | Produces the first plan, or a new plan after a real stop, within the authorized scope and runs the separate read-only review |
| `plan-ready RUN_ID` | The dispatcher does not move to implementation without a PASS from the separate review of the current revision |
| `automatic-plan RUN_ID` / plan JSON | A real stop, revision, review and permitted continue for project/split producers |
| `start RUN_ID` | The shared operator start entry; typed request, plan change, current review/source and cap gates |
| `project-step-verify RUN_ID CHECKPOINT_ID [continue\|retry] [NOTE]` | Verifies the bound result of a supervised job and lifts the wait; starts no process. A failed attempt needs `retry` and repair evidence |

If the project record `projects/<project>/supervision.json` contains `{"version":1,"mode":"step"}` it is bound immutably to a new request and passed to the children. A supervised code job runs sequentially in the project loop even if small; after every feature there is a persistent verification wait. Different bound backlog cards cannot be merged into the same feature; a sub-task of a card does not close the whole card. A failed first attempt is not retried automatically. `run --devam`, a panel start and the guard cannot skip this wait; a lost/broken wait record also produces a stop. The operator checks the product/QA/independent acceptance and the settled call cost, releases the related checkpoint with `project-step-verify`, reports the result to the user and calls `start` for the next step. This operator may be Codex; it is not a product flow that needs a new human approval at every step. Verification does not renew the total budget, the time or the review counters. An old/foreign result, a running owner, a worker session, missing acceptance or a pending call cost blocks progress. Without the setting the existing automatic project behaviour is kept.

In all supervised jobs, review/report included, the guard does not start or retry an `accepted/queued/retryable` run automatically; the queue does not take over the next supervised run either. The operator uses an explicit `start`. The native recovery of the same job interrupted while running is kept; that is not the automatic start of the next job. When the plan review ends with a valid verdict and a confirmed process close the phase clock stops; producing a revision does not consume review time. If a plan review phase limit (time/requests/tools/cost) is reached the record becomes `retryable` + `plan-review-limit-<time|requests|tools|cost>` and planning becomes `review-limit`: it is not a provider wait, the expired window is not reopened, no revision is produced, the guard does not retry; a new request is needed to continue.

`projects/<project>/qa-profile.json` can explicitly define a local acceptance phase: `{"version":1,"scope":"local","deferred":[{"path":"tests/test_live.py","sha256":"the file's 64-character SHA256 digest","reason":"separate live network phase"}],"excluded":[{"path":"archive/test_old.py","sha256":"SHA256 in the same form","reason":"historical diagnosis; outside active acceptance"}]}`. Real file digests are required; at most 20 files per list, at least one entry. The profile is frozen at acceptance, bound to the call permission and passed to the children. `deferred` files are still discovered; only SKIP records with the same content count as deferred and their count stays in the report. `excluded` removes only historical tests with the same source digest from the active discovery expectation; the files appear in the inventory, running them in this phase produces no acceptance. Any other SKIP, lost discovery, an error, no real PASS at all, a changed file or a profile widened later gives no acceptance. This profile is not a live source/publish acceptance; the result shows up with `acceptance_scope=local`, `deferred_tests` and the reason `qa-local-scope-live-tests-deferred`. Without the profile the existing strict full-scope behaviour is kept.

If an old run never recorded its source items, `cadre plan-backlog RUN_ID BACKLOG_PATH` is the explicit source selection; mentioning the file name in the request text does not replace this record. With a plan history a real stop via the existing `plan-change`/`plan-stop` is needed first. With only an old `plan.json`, the same JSON is first taken into the history with `save-plan`. Binding does not make an old PASS valid: a new plan revision mapping every item/hash/evidence to `source_items`, a separate `plan-review` and `plan-resume` are required. Old ids, the original request and the fixed total are kept; the old binding cannot be reused for another source or a changed backlog. The real model calls of this process are subject to their own definite permissions.

Reading a plan creates no call/reservation. If the revision and `plan.json` disagree, the controlled review/continue/start is blocked; recording the same current plan again can repair a half-written mirror. The review of a newly recorded revision is not carried over from the previous version. First/new plan generation and the separate review, project/split producers included, are bound to the same journal. Review rejections, an active owner/attempt, a changed source, an old revision, an expired time or the fixed total block side effects. If the mirror write is interrupted, the current journal is repaired without producing a paid plan again.

## Typed task input (local entry slice)

`cadre istek < request.json` and `python3 engine/lib/kosu.py request < request.json` use the same validator. The example is for an existing registered project; `/full/path/repo` must match the real `projects/lab/repo-path` record:

```json
{
  "submission_id": "unique-per-user-1",
  "project": "lab",
  "target_path": "/full/path/repo",
  "target_kind": "existing",
  "input_mode": "backlog",
  "prompt": "Finish the remaining work in the ready backlog.",
  "output": "An accepted change and its evidence",
  "acceptance": "",
  "preference": "balanced",
  "difficulty_override": null,
  "duration_minutes": 60,
  "budget_usd": "0.25",
  "backlog_path": "BACKLOG.md",
  "source_token": ""
}
```

`input_mode`: `backlog`, `goal`, `plan_only`; in `plan_only` mode the backlog path must be empty. In a review job in `goal` mode, `backlog_path` selects a source section only in the form `file.md#CARD-ID[,CARD-ID]`: the cards are validated against the backlog ids, every role gets the section text with line numbers, the whole file, Git objects and the run copy are closed to the tools; evidence can show only the selected lines. `preference`: `economic`, `balanced`, `strong`. The difficulty override is `null`, `easy`, `medium`, `hard`, `very_hard`; an automatic estimate does not count as done yet. `target_kind=new` records the intent of an empty/not yet created target, it does not create the target or the project. The budget is a finite, non-negative USD amount with at most six decimals, the time 1–43,200 whole minutes. A permission field is not accepted. The optional `scope_files` (allowed files) and `scope_tests` (required test files) are comma/line separated relative in-repo paths and apply only to a code job; the proposal carries this scope as `acceptance_scope`, the two approvals bind it with the request digest. With a bound scope, discovery limited to the explicit test path of the approved QA command is enough for the final acceptance; a change outside the allowed files (`scope-files-exceeded`), a required test that did not run (`scope-tests-not-run`), a weakened test or a non-independent review are still rejected. In a request without a scope, targeted discovery cannot get acceptance (`full-qa-required`); whole-product acceptance is separate. Provider scope, job type, the whole repo snapshot and the plan/permission review must be verified at the next gate.

A successful response is JSON with `run_id`, `status=waiting`, `reason=request-plan-gate`. When the same submission id and JSON are sent again the existing record is returned; a terminal record is not reopened. If the content changes a new submission id is needed. A field error produces JSON on stderr and exit 2; no executor/paid call/Git starts. Without two task-specific call approvals `run --devam` is blocked with exit 78. An approved run follows plan → separate review → plan delivery, or the isolated implementation/QA/final acceptance path; no additional human plan approval is asked for the review. If `source_token` is empty the selected source is taken at submission; the panel sends the token it verified in the summary and so rejects a backlog change. On a new empty target, plan-only delivery does not create the target; a code implementation waits at the first repo/commit permission gate. A code delivery is recorded as `reviewed-worktree`; it gives no commit/push/merge authority. CR-32's general environment/job type and real provider acceptance are still open.

## Current operating reference

### Functional QA and test maintenance

Code QA records, together with the test exit code, the really discovered/run/skipped ids, the product revision and the evidence hash. Standard pytest and unittest test names and an explicit `node --test` command are supported. Custom pytest file/function/class naming is not considered supported; since the scope cannot be verified, acceptance stops. Full acceptance requires all found test files/methods; a targeted child acceptance requires the changed/new tests. A child result does not replace full project acceptance. A new test outside testpaths, a partial SKIP/xfail, zero discovery or a hidden error exit gives no acceptance. Lint/syntax alone and an arbitrary command that cannot be observed become UNKNOWN; a code job cannot be turned into a report afterwards. A report's code checks are a justified NOT_APPLICABLE, its own evidence check is required.

Configured Ruff lint/format and mypy/pyright/basedpyright checks are recorded with the real exit and the path scope of the changed Python files for the supported explicit commands. Changed files are also checked with explicit file arguments, so directories the tool excludes by default do not count as implicit scope. A real tool error is not turned into uncertainty by the missing receipt of a check that then did not run; missing required evidence still gives no acceptance. An excluding configuration, complex shell/tool options, a quality command hidden in npm or an unsupported discovery form stays UNKNOWN; when a tool is missing nothing is installed. When extra quality scope evidence is required, green functional tests alone are not enough.

Authorized maintenance is not applied to a running run or one whose writer is locked. For an existing code run the user runs `cadre test-maintenance RUN_ID < decision.json`; this command does not change tests or start a model. JSON fields: `source_sha`, `revision` (`head` and `digest`), the full `command`, `reason`, `changes`. Each change carries `path`, the `purpose` of the old check, `preserved_criterion` and the `replacement`, `positive`, `negative`, `boundary` lists of real test ids. Positive and rejection/limit evidence cannot be covered by a single id. Free prompt text or a decision the model writes to a file does not count as authority.

The record is pinned with the RunStore lock, the original request hash and the full product/command; repeating the same decision is idempotent, a contradictory decision for the same revision is rejected. The replacement tests must pass in real QA; the independent judge must verify in an extra maintenance criterion that no required behaviour was lost. A changed source, product, command, missing negative evidence or an old receipt gives no exemption; a new revision is accepted again. Changing the evidence or the QA command later also invalidates the delivery acceptance.

First run only the modules related to the changed behaviour with `python3 engine/tests/paralel_kos.py <name-part>`; by default at most four workers, the explicit choice is `CADRE_TEST_ISCI`. The required final merge gate is `bash engine/tests/regression.sh`; it is not repeated for every small edit. For temporaries first create `.tmp/` at the repository root and use `TMPDIR="$PWD/.tmp"`. No PR is needed. If needed, choose the existing environments with `CADRE_UI_PYTHON` and `CADRE_TEST_PYTEST_PYTHON` and the archive with `CADRE_TEST_ARSIVI`. The test interpreter needs pytest, Ruff and BasedPyright; real quality tool tests do not count a missing dependency as SKIP. Python discovery, the three Node files, syntax and the local Git guard go into the same archive record; a required Python/UI/pytest SKIP is not PASS. The showcase CI runs only the `make test-fast` subset on macOS; in the full gate the real provider experiment stays a separate, permission-gated SKIP. The worker count `CADRE_TEST_ISCI` is passed from the shared gate to the subprocess; `paralel_kos.py` prints the effective value on the `isci:` line and the archive record carries the `isci` field (FIX-54).

The values below are a reference to the current code; they are not an end-to-end live acceptance claim. The goal and open gaps were in the contract and traceability documents of the private working repository; a summary of the open work is in CONTINUATION.md.
- The full-screen start and a task start can bring up the guards (saglik-nobet, kota-izle) from the code root; not every subcommand does this; liveness is `zincir/<name>.pid` + `.tik` (not pgrep).
- The coordinator keeps the Mac awake (a single `caffeinate`) and polls the guard every 30 min; the health guard scans run states on its ticks of 600 s by default and starts a crashed coordinator,
  a `retryable` run (at most 2 attempts) and a queued run. If disk < `CADRE_DISK_MIN_MB` (2048) the executor does not start.
- There is no local model. Without cloud capacity the executor does not start; the run waits with `butce-bekleme` (P3).
  If the cap is reached the run becomes `failed`/`no-capacity` (run.json `reason`). The disk threshold wait is 1 day.
- Budget: no daily share; Go is one pool (points, three windows); the OpenRouter and Zen share = the remaining balance; the shared monthly cash (OR + Zen)
  cap is $65 (`aylik_butce.py`, Go not included). Among paid candidates in the same quality tier the tight one falls back in the order; Claude
  links are not reordered. `cadre durum` shows the Go/OR/Zen shares.
- Delivery: the engine finishing normally is not an automatic push/merge. When the job ends the watcher offers `[p] push / [m] merge / [q]` on the same screen; `cadre` warns at start about
  "work waiting for delivery"; the old menu 5/6 or `cadre push|merge [project] [run_id]` lists finished jobs with numbers; for the chosen job it first asks "evet",
  then shows the full command to run and asks for a second "evet".
- A second task in the same project goes into the **queue** (`queued`) and starts by itself when the one ahead finishes. `cadre durum` → the `koşu:` line is structured.
- The per-run cloud spending cap comes from the level: simple `$1` · medium `$2` · hard `$5` · very hard/ultra `$10` (project files `kosu-tavan-usd` /
  `kosu-tavan-zor-usd`, for a single run by hand `CADRE_KOSU_TAVAN_USD`). The operator's starting total is fixed by default too; a plan estimate, the difficulty or an internal pocket extension cannot grow it. The main run, bound children, retries and check calls share the same limit. Cash USD and the Go/Claude usage equivalent are computed separately; the free request bucket does not enter the dollar total.
- In a project without a QA command, QA is derived at acceptance (see it with `qa_turet.py tara <repo>`); for stronger QA write `projects/<p>/qa-komut`.
- If the worktree environment differs from the user's environment write `projects/<p>/kurulum-komut`: it runs once at run start, as an approved action and in the same sandbox (network, package managers and writes to `node_modules`/`site-packages` are closed; it is for local preparation steps, not for installing dependencies). On failure the run stops with `kurulum-hatasi`; a timeout is a failure too and is retried with a new-generation approval (FIX-29). The QA command records the start result with the source/environment/command and output hash while there is no product. At project start an isolated source baseline is taken; a child shares it only with the same identity and re-measures with a different source/environment. A red baseline is kept as information; a new/changed error and a deleted test are a separate FAIL, an old red is not accepted. A targeted child QA does not count as a full project result. `CADRE_TABAN_QA=0` writes an explicit SKIP and does not open the code start gate; zero tests, broken/changed evidence or a wrong source are blockers too. ## Engine times and process lifetime

The engine's executor/disk wait/retry window is defined by `motor_sure_sn` in `sinirlar.json`: warning 2,700 s, hard end 5,400 s. `CADRE_WARN_SEC` and `CADRE_ABORT_SEC` set these values at the first execution start of the same job. The warning is disabled with 0; the hard end is a positive whole number of seconds. A warning larger than the hard end is clipped to it. The warning does not cut the job; the hard end applies to productive work too. The `motor_clock` in the task is kept across continue/restart; a larger setting later does not extend the time. Only the time between a confirmed `plan-stop` and a recorded `plan-resume` covering the same run is separated from the work window; an overlapping interval counts once. An ordinary retry/wait, a stop request alone, another run or a broken record gives no extra time; the cap is not reset. If a typed request/project or a recorded call permission ends earlier, that limit applies. The start worktree/baseline preparation and the plan/judge/QA commands use their own existing time gates; the engine window does not extend them. `cadre --help` shows the effective engine values from the same reader.

Liveness is a finite observation. A new and completed tool step is recorded progress; a repeat of the same input/output does not count as a new step. Only log/CPU/file metadata movement or an open connection is `unknown`, without movement `stalled`. These do not renew the progress clock. The adapted observation interval is between `CADRE_STALL_SEC` and three times this value; a broken/old liveness record cannot grow it without limit. The decision and the reason are written to the attempt's `canlilik.json` record. Time running out, a budget/permission block, cancel and a plan stop are separate decisions; fast spending alone is no reason to cut.

Test guards are bound to their own owner by the native process birth identity. During a long sleep the owner, home, code root and pidfile are checked again at intervals of at most five seconds; with a missing/wrong owner no guard is recreated. Exit cleanup signals only its own verified children. The target for a cancel to reach the persistent record is ≤2 s; the time of a full process cleanup including TERM→KILL is measured separately.

## Final review session

The final judge uses a separate clean read-only session in every round; the same model or family is acceptable. The family name is a heuristic, not evidence of independence. The native policy, the completed Attempt, a SID that is neither taken over nor repeated, the original request/criteria, the accepted plan, the source and the same product/QA revision must be recorded. An old `independent=True` alone does not open delivery; when the recorded request, plan, policy or session evidence changes the acceptance is invalid. If the judge changes the product the verdict is rejected; after an authorized repair step, QA and a new clean review are required. A format fix is also tested in a new read-only session with the full acceptance inputs. Budget, model permission and time gates apply to all these calls.

`cadre izin-cozumle ID TOKEN etkisiz|tamamlandi`: closes a permitted action left half done (in-flight/uncertain) after SIGKILL/timeout with an operator decision; denied if its owner is alive or from inside a run; `etkisiz` opens a new-generation approval (FIX-31).
